How CodeSentinel decides what matters

A CVSS 9.8 nobody exploits is less urgent than a CVSS 7.5 that ransomware crews use every week. CodeSentinel ranks findings by how likely they are to hurt you: known exploitation (CISA KEV), predicted exploitation (FIRST EPSS), and whether the issue is actually live in the code you ship.

Architecture

Priority tiers

P0

Critical now. Dependency CVE in CISA KEV; or CVSS ≥ 9.0 and EPSS ≥ 0.10; or a live-format credential in the current code; or SQL/command injection reached by user input (taint-confirmed).

P1

High. CVSS ≥ 7.0 with EPSS ≥ 0.01 (or no EPSS score); a secret still recoverable from git history; pull_request_target running untrusted code; broken cryptography; other high-severity rules.

P2

Medium. Other CVSS ≥ 4.0; unpinned third-party actions; containers running as root; weak cryptography; static-analysis hits without a confirmed taint path.

P3

Low / info. Everything else, including documentation placeholders such as AWS's example key.

Score and grade

risk = severity_weight × exploit × exposure severity_weight critical 10 · high 6 · medium 3 · low 1 · info 0.25 exploit 1 + 4 × EPSS (+2 if listed in CISA KEV) exposure 1.0 HEAD / direct · 0.6 transitive 0.5 history-only secret · 0.3 test files score = 100 − min(100, Σ risk ÷ 10) grade = A ≥ 90 · B ≥ 80 · C ≥ 70 · D ≥ 55 · F < 55

The gate fails when any open finding sits at or above the chosen tier (--fail-on p0|p1|p2, default P0). Suppressions in .codesentinel.yml need a justification and an expiry date; expired ones resurface automatically.

Data sources

  • OSV.dev: open vulnerability database aggregating GitHub Security Advisories, PyPA, npm, Go, Maven and more. Queried with /v1/querybatch.
  • FIRST EPSS: daily machine-learning estimate of the probability a CVE is exploited in the next 30 days.
  • CISA KEV: CVEs with confirmed exploitation in the wild, with remediation due dates for US federal agencies.
  • CycloneDX 1.6 for SBOM and CBOM; SARIF 2.1.0 for GitHub code scanning.
  • Regulatory context: CERT-In's SBOM guidelines (October 2024) and BOM guidelines v2.0 (July 2025, adding CBOM/QBOM/AIBOM/HBOM); SEBI's Cybersecurity and Cyber Resilience Framework (August 2024).

Ethics and data handling

  • Scan only code you own or are authorised to assess, or public repositories for research.
  • Secret values are never stored, logged or exported. Each one is reduced to a SHA-256 fingerprint and a redacted preview (first 4 + **** + last 4).
  • Secrets are never validated against provider APIs. Testing a stranger's key is unauthorised access even when the key is public.
  • Scanned code is never executed: no install scripts, builds or hooks. Clones are deleted after the scan.
