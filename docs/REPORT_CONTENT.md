## Abstract

Modern applications are assembled more than written: a typical service pulls in hundreds of open-source packages, runs in containers built from public base images, and is deployed by CI pipelines that execute third-party code with access to production credentials. Each of these is an attack path, and real incidents (Equifax 2017, Log4Shell 2021, the `tj-actions/changed-files` compromise of 2025) show that attackers use them. Existing open-source tools each cover one slice (secret scanners, dependency scanners, static analysers) and rank dependency vulnerabilities by CVSS severity alone, which buries the few actively exploited issues under hundreds of theoretical ones.

This project presents **CodeSentinel**, a unified supply-chain security gate. Given a GitHub URL, a source archive or a local path, it (i) detects leaked credentials in the working tree *and* in up to 500 commits of git history, using 27 provider signatures, generic assignment rules and Shannon entropy; (ii) inventories dependencies from six manifest/lockfile formats and enriches them live with OSV.dev advisories, FIRST EPSS exploitation probabilities and the CISA Known Exploited Vulnerabilities (KEV) catalogue; (iii) performs taint-aware abstract-syntax-tree analysis of Python and token-based analysis of JavaScript; (iv) audits Dockerfiles, docker-compose files and GitHub Actions workflows; and (v) builds a cryptography inventory with post-quantum readiness flags. Findings are ranked into exploit-aware priority tiers, combined into an A–F grade and a CI pass/fail decision, and exported as a CycloneDX 1.6 SBOM, a CycloneDX 1.6 CBOM, SARIF 2.1.0 for GitHub code scanning, CSV and a PDF report.

On a labelled ten-commit demonstration repository containing 56 planted issues and 3 decoys, CodeSentinel achieved precision, recall and F1 of 1.00 in every module, flagged none of the decoys, and identified all three CISA-KEV-listed CVEs (Log4Shell CVE-2021-44228, CVE-2021-45046 and the libwebp CVE-2023-4863). On two real, intentionally vulnerable applications it scanned OWASP PyGoat (46 components, 153 CVEs, 500 commits of history) in 14.1 s and OWASP Juice Shop (170 components, 1,467 files) in 36.7 s, surfacing taint-confirmed SQL and command injection, a KEV-listed library CVE and a private key committed to Terraform. The gate turns FAIL to PASS when the demonstration repository is remediated.

**Keywords:** software supply chain, secret detection, EPSS, CISA KEV, SBOM, CBOM, CycloneDX, SARIF, static analysis, DevSecOps.

## 1. Introduction

Software supply-chain security is the practice of protecting everything that goes into a release: first-party code, third-party packages, build and CI infrastructure, and the credentials that tie them together. The attack surface has grown with the industry's reliance on open source and automation. A single Python web application can depend on dozens of packages that each depend on more; a single GitHub Actions workflow can execute code from several third-party repositories with write access to the source tree and to deployment secrets.

Three trends make this a pressing problem:

1. **Credentials leak at scale and stay valid.** GitGuardian's *State of Secrets Sprawl 2025* reported 23.8 million secrets leaked on public GitHub in 2024, a 25% increase year on year, and found that about 70% of secrets leaked in 2022 were still valid. Developers frequently "fix" a leak by deleting the line, but the secret remains in every clone of the history.
2. **Vulnerability volume outpaces remediation capacity.** Tens of thousands of CVEs are published each year. Severity scores (CVSS) describe how bad a vulnerability *could* be, not how likely it is to be used. Teams that patch by CVSS alone spend effort on issues that are never exploited while missing ones that are.
3. **Regulators now expect inventories.** CERT-In's *Technical Guidelines on SBOM* (October 2024) and its *BOM Guidelines v2.0* (July 2025) extend bill-of-materials expectations from software components to cryptography (CBOM), quantum readiness (QBOM), AI (AIBOM) and hardware (HBOM). SEBI's Cybersecurity and Cyber Resilience Framework (August 2024) requires regulated entities to obtain SBOMs for core and critical software.

CodeSentinel addresses these together, as a single gate that a developer can run locally, a CI pipeline can enforce, and an auditor can read.

## 2. Problem Statement

Given a software repository, determine automatically and within CI time budgets:

- which credentials are exposed in the current code or recoverable from version history, without ever storing or using those credentials;
- which third-party components are vulnerable, and which of those vulnerabilities are being exploited or are likely to be exploited, together with the exact fix;
- which first-party code patterns, container definitions and CI workflows create injection, misconfiguration or supply-chain risk;
- which cryptographic algorithms are in use and whether they are broken, weak or quantum-vulnerable;

and combine these into a prioritised, explainable result: a grade, a pass/fail decision with reasons, and standards-compliant artefacts (SBOM, CBOM, SARIF) that other tools and auditors can consume.

Existing open-source tools solve parts of this in isolation, with different output formats and ranking schemes, and none of the commonly used free tools combines exploit-aware prioritisation (EPSS + KEV) with secrets history, code, CI and cryptography in one gate.

## 3. Objectives

1. Detect leaked secrets in HEAD and in git history across at least 20 provider formats, with entropy analysis and false-positive controls, and never persist a raw secret.
2. Parse Python, JavaScript, Java and Go manifests and lockfiles into a component inventory with Package URLs and direct/transitive relationships.
3. Enrich components with live data from OSV.dev, FIRST EPSS and CISA KEV, with caching, retries and graceful degradation.
4. Implement AST-based Python SAST with taint tracking and token-based JavaScript SAST, each rule mapped to CWE and OWASP Top 10:2021 with remediation guidance.
5. Audit Dockerfiles, docker-compose files, committed `.env` files and GitHub Actions workflows, including the controls that would have prevented the `tj-actions` incident.
6. Inventory cryptographic usage and export a CycloneDX 1.6 CBOM with approved/weak/broken classification and quantum-vulnerability flags.
7. Define a transparent exploit-aware prioritisation model (P0–P3), a numeric risk score, an A–F grade and a configurable CI gate.
8. Produce a CycloneDX SBOM, SARIF 2.1.0, CSV and a PDF report, and provide a web interface, a CLI and a GitHub Actions integration.
9. Evaluate precision and recall against labelled ground truth (targets: recall ≥ 0.95, precision ≥ 0.90) and validate on real public repositories.

## 4. Literature and Industry Review

**4.1 Secret leakage.** Meli, McNiece and Reaves (NDSS 2019) showed that thousands of new API keys and private keys leak on GitHub every day and that most remain valid for a long time. GitGuardian's annual *State of Secrets Sprawl* reports quantify the trend at internet scale: 23.8 million secrets leaked publicly in 2024 (+25%), with roughly 70% of the secrets leaked in 2022 still valid. Tools such as gitleaks and TruffleHog combine regular expressions with entropy; GitHub push protection blocks known formats at push time. The literature consistently notes two hard problems: false positives from high-entropy non-secrets (hashes, IDs) and the persistence of secrets in history after deletion.

**4.2 Vulnerability databases: OSV.** The Open Source Vulnerabilities (OSV) project, launched by Google in 2021, aggregates advisories from GitHub Security Advisories, PyPA, RustSec, the Go vulnerability database, npm and others into one schema with machine-readable affected-version ranges. Its `querybatch` API maps (ecosystem, package, version) tuples to advisory IDs, and each advisory carries aliases (CVE IDs), CVSS vectors and fixed versions.

**4.3 Exploit Prediction Scoring System (EPSS).** EPSS, maintained by FIRST, is a data-driven model that estimates the probability that a CVE will be exploited in the wild in the next 30 days, using features such as vendor, exploit-code availability and observed exploitation activity. Published work by the EPSS SIG shows that prioritising by EPSS achieves far better coverage of exploited vulnerabilities per unit of remediation effort than prioritising by CVSS thresholds alone. EPSS scores are recalculated daily and published through a free API.

**4.4 CISA Known Exploited Vulnerabilities (KEV).** CISA's KEV catalogue, created alongside Binding Operational Directive 22-01 in November 2021, lists CVEs with reliable evidence of active exploitation and sets remediation due dates for US federal agencies. It is small (1,754 entries in the catalogue fetched for this evaluation) and authoritative, which makes it an effective "patch now" signal.

**4.5 CVSS.** The Common Vulnerability Scoring System (v3.1, and v4.0 from November 2023) rates the technical severity of a vulnerability from a vector of metrics. It is widely used but, by design, does not measure likelihood of exploitation; FIRST's own guidance recommends combining it with threat intelligence.

**4.6 SBOM and CBOM standards.** CycloneDX (OWASP) and SPDX (Linux Foundation) are the two dominant SBOM formats. CycloneDX 1.6 (2024) added first-class cryptographic-asset components with `cryptoProperties` (asset type, primitive, mode, parameter set, crypto functions, classical and NIST quantum security levels), enabling a cryptographic bill of materials (CBOM). CBOMs support crypto-agility programmes and migration to post-quantum algorithms standardised by NIST in 2024 (FIPS 203, 204, 205).

**4.7 Indian regulatory context.** CERT-In's *Technical Guidelines on SBOM* (October 2024) define minimum SBOM elements and processes for Indian organisations; its *BOM Guidelines v2.0* (July 2025) extend the scope to CBOM, QBOM, AIBOM and HBOM. SEBI's CSCRF (August 2024) mandates SBOMs for core and critical applications at regulated entities. A tool that emits CycloneDX SBOM and CBOM from the same scan directly supports these requirements.

**4.8 Incidents that motivate the design.**

- *Equifax (2017).* Attackers exploited CVE-2017-5638 in Apache Struts two months after a patch was available, exposing personal data of about 147 million people. The lesson: known, exploitable dependency vulnerabilities must be found and patched quickly, and prioritisation matters.
- *Log4Shell (December 2021).* CVE-2021-44228 in Apache Log4j 2 allowed remote code execution through a logged string. Organisations struggled because they did not know where Log4j was used, which is the core argument for SBOMs. It is in KEV and has an EPSS score close to 1.
- *tj-actions/changed-files (March 2025).* CVE-2025-30066: attackers modified the version tags of a GitHub Action used by more than 23,000 repositories so that it dumped CI secrets into build logs. Repositories that pinned actions to a full commit SHA were unaffected. This motivates CodeSentinel's CI workflow auditor.

**4.9 Static analysis.** Bandit uses Python's AST for security linting; Semgrep provides pattern-based multi-language analysis; CodeQL performs semantic data-flow analysis. AST-based analysis avoids the false positives of regular expressions on comments and strings, and taint tracking separates exploitable sinks from constant ones.

**4.10 SARIF.** The Static Analysis Results Interchange Format 2.1.0 (OASIS) is the standard result format consumed by GitHub code scanning, Azure DevOps and many IDEs, so a tool that emits SARIF integrates with existing developer workflows.

## 5. Proposed System

CodeSentinel is a single application with three front ends (web UI, CLI, GitHub Actions) over one scan pipeline:

1. **Ingest** the target safely (clone with limits, extract archives with zip-slip protection, or read a local directory).
2. **Load policy** from `.codesentinel.yml` (ignored paths, suppressions with mandatory justification and expiry, default gate level).
3. **Scan** with five modules: secrets (HEAD + history), dependencies (+ live intel), SAST (Python + JS), IaC/CI, and cryptography.
4. **Normalise** findings into one schema, merge cross-module duplicates, apply suppressions and compute stable fingerprints.
5. **Prioritise** into P0–P3 using exploit signals and exposure, compute a risk score, an A–F grade and the gate decision.
6. **Export** SBOM, CBOM, SARIF, CSV, JSON and PDF; store everything for history and diffing.

The novelty lies not in any single detector but in the **unified, exploit-aware decision**: a KEV-listed CVE, a live secret in HEAD and a taint-confirmed SQL injection all land in the same P0 tier with the same explainable rule, while thousands of low-likelihood issues are ranked below them.

## 6. Architecture

The system follows a layered architecture (Figure: `docs/ARCHITECTURE.md`, component diagram; the UI's Methodology page shows the same flow, Figure 6):

- **Application:** FastAPI routes and REST API, a thread-pool job runner that records stage progress, triage and history-diff services.

- **Output:** CycloneDX SBOM/CBOM, SARIF, CSV, JSON and PDF exporters.

## 7. Module Design

### 7.1 Secret Detection Engine

*Detection.* Each line is checked by three layers in order, with overlapping matches suppressed so the most specific wins:

1. **27 provider signatures** with named rule IDs: AWS access key IDs (`AKIA`/`ASIA` + 16) and secret keys (with an "aws" context keyword and an entropy floor), GitHub (`ghp_`, `gho_`, `ghs_`, `ghu_`, `github_pat_`), GitLab, Slack tokens and webhooks, Stripe live/test keys, Google API keys, Twilio, SendGrid, OpenAI-style and Anthropic keys, Razorpay, npm, PyPI, Telegram, Discord webhooks, Azure storage keys, JWTs, PEM private-key headers, and database URIs with inline passwords (PostgreSQL, MySQL, Redis, AMQP, MSSQL, MongoDB).
2. **Generic assignments** such as `password = "..."`, `api_key: '...'` and unquoted `.env` values, excluding UI labels, URLs, identifiers, function calls and single dictionary words.
3. **Shannon entropy** on quoted strings of length ≥ 20 when the line mentions a credential keyword:

   H(s) = −Σ pᵢ log₂ pᵢ, where pᵢ is the frequency of character i.

   Thresholds are 4.3 bits/char for base64-alphabet strings and 3.0 for hexadecimal strings (hex has a maximum of 4 bits/char). SRI hashes (`sha512-...`), UUIDs and file paths are excluded.

*False-positive controls.* Lockfiles, minified bundles, binaries, `node_modules`, `vendor` and files over 1 MB are skipped; translation files only receive provider-signature checks; placeholders (`EXAMPLE`, `changeme`, `your_api_key`, `<...>`, repeated characters) are downgraded to *info* rather than hidden, so AWS's documentation key `AKIAIOSFODNN7EXAMPLE` is visible but never blocks a build; `codesentinel:ignore` suppresses a line.

*History.* A single streamed `git log -p --unified=0 --diff-filter=AM -n 500` call yields every added line of every commit with its file and line number. Hits whose fingerprint is not present in HEAD become *historical* findings pinned to the commit that introduced them (SHA and author date); hits that are also in HEAD annotate the HEAD finding with "introduced in".

*Privacy.* Only a SHA-256 fingerprint and a redacted preview (first 4 + `****` + last 4; less for short values) leave the detector. Code snippets from every module pass through a redaction function. Secrets are never sent to providers for validation.

### 7.2 Dependency Vulnerability Scanner

*Parsers.* `requirements*.txt` (pins, ranges, extras, environment markers, hashes, `-r` includes), `Pipfile.lock` (direct-ness from `Pipfile`), `poetry.lock` (direct-ness from `pyproject.toml`, dependency graph), `package-lock.json` v1 (nested tree) and v2/v3 (flat `packages` map with Node's resolution algorithm for the dependency graph), `package.json` (ranges resolved to the minimum satisfying version and flagged `version_inferred`), `pom.xml` (property substitution including parent and project properties, `dependencyManagement`, scopes) and `go.mod` (`// indirect` → transitive). Every component gets a Package URL such as `pkg:pypi/django@3.2.0` or `pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1`.

*Intelligence.* Components are sent to OSV `querybatch` in chunks of 500; advisory details are fetched concurrently (16 in flight). Advisories that are aliases of each other (for example a GHSA and a PYSEC record for the same CVE) are merged with a union-find over aliases so each vulnerability is reported once. CVSS base scores are computed from v3.x or v4.0 vectors with the `cvss` library, falling back to the advisory's severity label. EPSS scores are fetched in batches of 100 CVEs; the KEV catalogue is downloaded once and cached for 24 hours. All responses go into the `FeedCache` table with a TTL; failures are retried with exponential backoff, and a feed outage marks findings `intel_partial` instead of failing the scan.

*Output.* Each finding carries package, version, ecosystem, PURL, all advisory IDs and CVEs, CVSS score and vector, EPSS score and percentile, KEV flag with due date and ransomware use, the smallest fixed version above the installed one (computed from OSV affected ranges with ecosystem-specific version ordering), the exact upgrade command (`pip install "django>=3.2.14"`, `npm install lodash@4.17.21`, an npm override for transitive packages, `mvn versions:use-dep-version …`, `go get …`) and reference links.

### 7.3 Static Analysis

*Python (AST).* The analyser parses each file with `ast`, resolves import aliases (`from subprocess import run as r`) and walks functions in order, maintaining per-function sets of **tainted names** (assigned from `request.args/form/json/...`, `request.get_json()`, `input()`, `sys.argv`, or web-route parameters) and **dynamic-SQL names** (built with f-strings, `%`, `+` or `.format`). Thirteen rules each carry a CWE, an OWASP Top 10:2021 category, a description, remediation text and a secure code example: SQL injection (CWE-89), command injection (CWE-78), eval/exec (CWE-95), pickle and unsafe YAML deserialisation (CWE-502), disabled TLS verification (CWE-295), debug mode (CWE-489), hard-coded `SECRET_KEY` (CWE-798), non-cryptographic random for tokens (CWE-338), MD5/SHA-1 password hashing (CWE-328), `tempfile.mktemp` (CWE-377), `assert` for authorisation (CWE-703) and path traversal (CWE-22). When tainted data reaches a sink, severity is raised and the finding is marked `tainted`; a tainted SQL or command injection is P0.

*JavaScript/TypeScript (tokens).* A small tokenizer removes comments while preserving strings, template literals and line numbers. Eight rule families detect `eval`/`new Function`, `child_process.exec` with interpolation, `innerHTML`/`outerHTML`/`document.write`/`dangerouslySetInnerHTML` with non-literal values (CWE-79), SQL template literals passed to `.query()`, `jwt.verify` without an `algorithms` allow-list or allowing `none` (CWE-347), `Math.random` in token/session contexts, wildcard CORS with credentials (CWE-942) and hard-coded JWT secrets.

### 7.4 IaC and CI/CD Auditor

*Dockerfile:* final-stage `USER` missing or root, `:latest`/untagged base images (aliases, digests and `scratch` excepted), `ADD` from URLs, `curl | sh`, secrets in `ENV`/`ARG`, `EXPOSE 22`, missing `HEALTHCHECK`, `apt-get install` without list cleanup. *docker-compose:* `privileged: true`, `network_mode: host`, Docker-socket mounts, literal passwords in `environment`. *`.env`:* a tracked `.env` file is high severity (untracked, git-ignored files are not "committed"). *GitHub Actions:* third-party actions not pinned to a 40-character SHA (the remediation text cites CVE-2025-30066), `pull_request_target` combined with a checkout of the PR head, untrusted `github.event.*` expressions inside `run:` blocks (script injection; the same expression in `env:` is the safe pattern and is not flagged), missing or `write-all` permissions, and secrets echoed in `run:`.

### 7.5 Cryptography Inventory and CBOM

The crypto module recognises hashing (MD5, SHA-1, SHA-2, SHA-3, BLAKE2), password KDFs (bcrypt, Argon2, scrypt, PBKDF2 with iteration counts), symmetric ciphers and modes (AES in ECB/CBC/GCM/CTR/..., DES, 3DES, RC4, Blowfish, ChaCha20), asymmetric keys (RSA with key size, ECC curves, Ed25519/X25519, DSA), TLS protocol versions and disabled certificate verification, JWT algorithms, and randomness sources (`random`/`Math.random` in security contexts versus `secrets`/`os.urandom`/`crypto.randomBytes`) in both Python (AST) and JavaScript. Each occurrence is classified:

| Class | Examples |
|---|---|
| broken | MD5, DES, RC4, AES-ECB, RSA < 2048, SSLv3/TLS 1.0/1.1, verification disabled, JWT `none` |
| weak | SHA-1, 3DES, Blowfish, PBKDF2 < 100,000 iterations, P-192/P-224, DSA, Mersenne Twister for tokens |
| approved | SHA-256+, AES-GCM/CBC/CTR, ChaCha20, bcrypt, Argon2id, RSA ≥ 2048, P-256+, Ed25519 |

RSA, DSA, DH and elliptic-curve assets are additionally flagged `quantum_vulnerable` with NIST quantum security level 0, supporting a post-quantum migration plan (CERT-In BOM v2.0's CBOM/QBOM scope). The CBOM groups occurrences into one `cryptographic-asset` component per configuration with `cryptoProperties.algorithmProperties` (primitive, parameter set, mode, crypto functions, classical and quantum security levels) and `evidence.occurrences` (file and line).

### 7.6 Risk Scoring, Grade and Gate

| Tier | Rule |
|---|---|
| P0 | KEV-listed dependency CVE; or CVSS ≥ 9.0 and EPSS ≥ 0.10; or live-format secret in HEAD; or taint-confirmed SQL/command injection |
| P1 | CVSS ≥ 7.0 with EPSS ≥ 0.01 (or no EPSS); historical secret; `pull_request_target` misuse; broken crypto; other high/critical rules |
| P2 | other CVSS ≥ 4.0; unpinned actions; root containers; weak crypto; untainted SAST; other medium rules |
| P3 | everything else, including placeholders |

risk = severity_weight × (1 + 4·EPSS + 2·[KEV]) × exposure, with weights critical 10, high 6, medium 3, low 1, info 0.25 and exposure 1.0 (HEAD, direct), 0.6 (transitive), 0.5 (history-only secret) or 0.3 (test files). Score = 100 − min(100, Σrisk/10); A ≥ 90, B ≥ 80, C ≥ 70, D ≥ 55, otherwise F. The gate fails if any open finding is at or above the configured tier (`--fail-on p0|p1|p2`, default P0). Suppressions in `.codesentinel.yml` require a justification and an expiry date; expired suppressions resurface automatically. Web-UI triage (false positive / accepted risk, justification required) re-evaluates the grade and gate immediately.

## 9. Results and Evaluation

### 9.1 Ground-truth evaluation

The demonstration repository `demo/vulnerable-shop` ("KiranaKart", a Flask storefront, a Node order API and a Java reports job) has 10 commits by two authors over five months and contains 39 labelled code-level issues (7 secrets including 3 that exist only in history and 1 documentation placeholder, 17 SAST, 13 IaC/CI, 2 crypto), 17 genuinely vulnerable packages (9 PyPI, 7 npm including 3 transitive, 1 Maven) and 3 decoys. Matching is by rule + file + line (±1), by rule + file for history-only secrets, and at package level for dependencies.

| Module | Planted | TP | FP | FN | Precision | Recall | F1 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Secrets (HEAD + history) | 7 | 7 | 0 | 0 | 1.00 | 1.00 | 1.00 |
| SAST (Python + JS) | 17 | 17 | 0 | 0 | 1.00 | 1.00 | 1.00 |
| IaC / CI | 13 | 13 | 0 | 0 | 1.00 | 1.00 | 1.00 |
| Crypto | 2 | 2 | 0 | 0 | 1.00 | 1.00 | 1.00 |
| Dependencies (packages) | 17 | 17 | 0 | 0 | 1.00 | 1.00 | 1.00 |
| **Overall** | **56** | **56** | **0** | **0** | **1.00** | **1.00** | **1.00** |

None of the three decoys was flagged: a live-format Stripe key in a comment marked `codesentinel:ignore`, a sha512 SRI integrity hash in `package-lock.json`, and a parametrised SQL query (`WHERE id = ?` with a tuple).

The scan inventoried 32 components (15 direct, 17 transitive), found 181 distinct advisories covering 179 CVEs in 17 components, and populated EPSS for 177 of them. Three are in CISA KEV: CVE-2021-44228 and CVE-2021-45046 in log4j-core 2.14.1 and CVE-2023-4863 (libwebp heap overflow) in Pillow 8.0.0. The gate failed with 11 P0 findings (3 KEV CVEs, 4 Django CVEs with CVSS ≥ 9 and EPSS ≥ 0.10, a Stripe live key and a database password in the committed `.env`, and taint-confirmed SQL and command injections). Grade: F. Total scan time was 1.3 s with a warm feed cache (about 11 s on a cold cache, dominated by OSV advisory downloads).

Prioritisation in practice: the top of the list is log4j-core CVE-2021-44228 (CVSS 10.0, EPSS 1.00, KEV, risk 70.0), CVE-2021-45046 (CVSS 9.0, KEV) and Pillow CVE-2023-4863 (CVSS 8.8, KEV), ahead of several CVSS 9.8 Django and PyYAML issues whose EPSS is below 0.10. A CVSS-only ranking would have placed the actively exploited libwebp CVE (8.8) 23rd, behind 22 higher-scored but far less likely issues; CodeSentinel ranks it third.

**Remediation.** The remediated twin `demo/vulnerable-shop-fixed` (current dependency versions, parametrised queries, `yaml.safe_load`, PBKDF2-SHA256 with 600,000 iterations, AES-GCM, RSA-3072, a non-root container with a health check, SHA-pinned workflows with least-privilege tokens) scores **A (100) and passes** with 56 components and no known CVEs. Applying the same fixes as a new commit on the vulnerable repository (`make_demo_repo.py --remediate`) and rescanning gives a history diff of 214 fixed, 6 unchanged and 4 new findings. The unchanged and new items are the previously committed secrets, which now appear as history-only P1 findings. This demonstrates the key teaching point: deleting a secret does not remove it, so the credential must be rotated.

### 9.2 Real-world validation

|---|---:|---:|---:|---:|---:|---|---|---:|

| OWASP Juice Shop (HEAD only, 1,467 files) | 170 | 19 | 40 | 0 | 39 / 43 | 1 / 38 / 89 / 5 | F | 36.7 s + 7.8 s clone |

Spot checks of every P0 confirmed true positives. In PyGoat: SQL built by string concatenation from request parameters and passed to Django's `objects.raw()` (`introduction/views.py:162` and `:878`), a shell command built from a request parameter (`:430`), Pillow 9.4.0 affected by the KEV-listed CVE-2023-4863, and Django CVE-2025-64459 (CVSS 9.1, EPSS 0.19). In Juice Shop: an RSA private key embedded inline in `infrastructure/terraform/networking.tf`. Juice Shop commits no lockfile, so its 170 components come from `package.json` ranges resolved to minimum versions (flagged `version_inferred`).

During validation Juice Shop exposed two weaknesses that were then fixed and re-measured: translation files produced generic-password false positives (`"LABEL_PASSWORD": "Contraseña"`), and a generic-assignment regular expression backtracked quadratically on long digit-only lines, making secret scanning take 90 s. Restricting translation files to provider signatures, ignoring UI-label keys and single dictionary words, anchoring the expression and adding literal pre-filters reduced the secret findings from 116 to 41 genuine hard-coded credentials (seed-user passwords, TOTP secrets in tests, the Terraform key) and the stage time from 90 s to 4.6 s.

### 9.3 Standards conformance and hygiene

The SBOM and CBOM for the vulnerable shop validate without errors against the official CycloneDX 1.6 JSON schema (`bom-1.6.schema.json`), and the SARIF log validates against the OASIS SARIF 2.1.0 JSON schema. Structurally they contain the required elements (`bomFormat`, `specVersion`, `urn:uuid` serial number, metadata, components with PURLs, dependency graph, vulnerabilities with CVSS ratings and affected references; `cryptographic-asset` components with `cryptoProperties` and `evidence.occurrences`). The SARIF log conforms to 2.1.0 with one run, rules carrying `helpUri`, CWE tags and `security-severity`, and results with physical locations and partial fingerprints, as required by `github/codeql-action/upload-sarif`. The PDF report for the vulnerable shop is 21 pages with charts. A search of 269 artifacts (the SQLite database, every export format, the server logs, and every rendered report and finding page and API response) plus the extracted PDF text found no planted secret value anywhere. CodeSentinel scans its own repository in CI with grade A and no P0 or P1 findings (two documentation placeholders at P3).

## 11. Conclusion

CodeSentinel shows that a single, explainable gate can cover the main software supply-chain risk areas with live, real-world intelligence. Combining CVSS with EPSS and the CISA KEV catalogue moves actively exploited issues (Log4Shell, the libwebp heap overflow) to the top of hundreds of findings, which is exactly where a time-constrained team needs them. Scanning git history surfaces credentials that a deletion did not remove. AST-based taint tracking distinguishes exploitable injections from constant queries. A CycloneDX SBOM and CBOM from the same scan support current Indian regulatory expectations (CERT-In BOM v2.0, SEBI CSCRF). The tool met its evaluation targets on labelled data (precision and recall 1.00, no decoys flagged), produced verified true-positive P0 findings on two real applications within CI time budgets, and enforces its own gate on its own repository.

## 12. Future Scope

1. **Reachability analysis:** call-graph analysis to report only vulnerable functions that the application actually calls.
2. **Container image scanning:** inventory OS packages in built image layers, not just Dockerfile text.
3. **AIBOM:** detect AI models, datasets and their licences and provenance, completing CERT-In BOM v2.0 coverage.
4. **Consent-based secret validity checks** for organisations scanning their own estate, to separate live from revoked credentials.
5. **Inter-procedural and cross-file taint tracking**, and AST-based JavaScript/TypeScript analysis.
6. **IDE plugin and pre-commit hook**, to catch secrets before they are committed.
7. **VEX output** so that accepted risks and non-exploitable findings can be communicated to SBOM consumers.
8. **Organisation dashboards** aggregating many repositories, with PostgreSQL and a distributed job queue.
